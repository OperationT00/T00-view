# 来源无关的名称解析模块

已实现规则版本：`name-v1`。本模块生成候选，不创建词表、收藏、位置或导入批次。PikPak、本地文件选择和确认入库由后续适配层实现。

## 模块边界

`parsing/ResourceNameParser` 为纯 Java 类，无 Spring、JDBC、网络或文件系统依赖。调用方提供 `Input` 和不可变词表快照，可单独测试，也可由未来本地／PikPak 适配器共用。

`ParsingController` 从现有 FacetService 读取一致性词表快照，转换成解析器自己的 `Entry`，批量调用核心。依赖方向为 Web／词表适配层 → 解析核心；核心不依赖六维业务服务。

管理员页面“来源解析”支持名称／路径清单及显式指定的单个分类文件夹。当前是解析预览工具，不是已完成的本地／PikPak 导入入口。

## 接口

`POST /api/v2/parsing/preview`，仅 ADMIN，要求登录和 CSRF，每批 1–100 项。

```json
{
  "items": [{
    "key": "1",
    "fileName": "博主甲-高跟鞋-黑丝-zw.mp4",
    "relativePath": "王者荣耀-公孙离-离恨烟/博主甲-高跟鞋-黑丝-zw.mp4",
    "classificationFolder": "王者荣耀-公孙离-离恨烟"
  }]
}
```

fileName 必填、最大255字符；classificationFolder可空、最大512；relativePath可空、最大4096；key可空、最大128。文件名和分类文件夹不能包含路径分隔符；拒绝控制字符及超过32段的名称。路径是文字证据，不被访问。批内任何非法输入返回400，不产生部分业务写入。

返回 `{ruleVersion,items}`。每项含原名称、路径、文件形式提示、candidates和issues。候选含dimension、text、origin（FOLDER／FILE）、status、matches、ownerText；匹配记录包含实体ID、版本和上下文。状态为MATCHED／PROPOSED／AMBIGUOUS／DISABLED。MATCHED也只代表名称匹配，不代表内容经过验证。

## 当前规则与限制

- 目录按作品－角色－可选皮肤解释，使用词表和归属关系评估分隔位置。多个有依据的分法并存时提示歧义；空词表的两／三段目录按模板形成待确认候选。
- 创作者优先匹配已有完整前缀名称（支持名称含横杠）；否则首段形成待确认候选并提示检查。
- 目录无皮肤时，文件名可补皮肤；已有同名皮肤仅按当前角色匹配。跨角色、目录与文件冲突明确提示。
- 服装和类型按完整字段匹配。内置候选词为用户已有示例：cos／zw／do、高跟鞋／黑丝／白丝／旗袍；缺少实体时仅建议新建，不自动写词表。
- 第一个未识别字段在目录有角色、无皮肤时可建议为皮肤，同时产生SKIN_ASSUMPTION；该候选不能当作可靠识别直接入库。
- 不自动拆“黑丝高跟鞋”等连续文字；不自动识别多个创作者或别名；未知片段保留。词表中包含横杠的名称使用最长完整匹配，首版不穷举文件名的所有语义切分，需要人工复核。
- 已知视频扩展名提示VIDEO；图片提示需要确认图集分组，保持OTHER；未知扩展名保留并提示。文件形式不证明文件真实内容。
- 六维继续保留，zw归TYPE；不由角色／皮肤推断服装或内容类型。

后续入口可提供统一元数据，再接草稿修正与入库。最新 [PikPak 分享管理与观看设计](pikpak-share-playback-design.md) 本期只做链接管理和观看，名称解析及收藏联动留待后续；本解析器保持独立。解析预览没有持久化，页面离开后需重新解析。

## 验证

本次完整后端测试共75项，无失败、错误或跳过：包含12项纯解析单元测试，以及真实MySQL环境下的接口权限、CSRF、输入校验和预览不写入业务数据检查。前端TypeScript检查及生产构建通过。

隔离测试库的8项浏览器检查通过：管理员入口、示例七项候选、zw归TYPE、不新增收藏、手机布局、输入变化清空旧结果、未知片段展示和无JavaScript运行错误。
